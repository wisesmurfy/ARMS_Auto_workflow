# 리뷰 규칙 (항상 로드)

## 단위
- Unit = 데이터 변환 1개 = 파일 1개 = 커밋 1개, 추가 ~150줄 이하. 넘으면 먼저 쪼갠다
- Unit을 만들면 멈추고 리뷰 카드를 준다. "OK" 전에는 커밋·다음 Unit 금지
- 지금 목줄 레벨: **Level 1 (Unit마다 멈춤)**. 🟡·🟢 묶음 리뷰(Level 1-묶음)는 사용자가 정할 때만
- 레벨은 사용자만 바꾼다

## 리뷰 카드 (설명은 쉬운 말과 비유로. 전문 용어는 처음 나올 때 풀어 쓴다)
1. 한 줄 요약
2. 데이터 흐름 (무엇이 들어와서 무엇이 나가나)
3. 읽는 순서 (파일:줄)
4. ✅ 적용한 것 / ↩ 고르지 않은 선택지 — 왼쪽은 이미 코드에 반영됨. 오른쪽으로 바꾸려면 사용자가 말하면 같은 Unit 안에서 고친다
5. 직접 해보기 (명령 + 기대 결과)
6. 질문을 두 칸으로 나눈다
   - 6-1. ⭐ 결정·검토 필요: 사용자 답이 필요한 것. 답이 없을 때 어떻게 진행하는지도 적는다. 없으면 "없음"
   - 6-2. 이해 확인 (선택, 1~2개): 답하지 않아도 되는 퀴즈. 가끔 "이 줄은 무엇을 돌려주나?" 같은 읽기 질문
7. 불확실·위험
8. 🌱 처음 나온 문법 (선택, 최대 2개) — `docs/learning/python-glossary.md`를 보고 새 것만.
   두 번째는 "사전 #n" 링크만, 세 번째부터는 언급하지 않는다. 문법 설명은 코드 주석에 넣지 않는다

## 리뷰 깊이
- 🔴 정독: schemas.py, llm.py, prompts/*, 핵심 로직 폴더, pipeline.py, 보안 설정  ← 프로젝트 시작 때 실제 파일로 고친다
- 🟡 보통: tests/*, 입구(cli.py·api.py 등)
- 🟢 훑기: pyproject.toml, .gitignore, 문서

## 비판을 받았을 때
- 바로 "맞습니다"라고 하지 않는다. 찬성 근거와 반대 근거를 함께 제시하고 결정은 사용자가 한다
- 수정은 같은 Unit 안에서 하고 카드를 다시 낸다. 설계 방향이 바뀌면 ADR 초안을 쓴다
- Q&A와 결정은 PR 설명의 "리뷰 기록" 칸에 남긴다
